# RIS

> 基于 Intel RealSense 深度相机与 YOLOv8 的目标检测与空间定位实验仓库。

目前这个仓库还处在原型验证阶段，但关键链路其实已经被你拆开跑通过一遍了：相机取流、目标检测、框中心点提取、深度对齐、距离估计，以及将像素坐标转换为相机坐标 / 极坐标。

## 项目现状

从现有脚本来看，这个项目的目标已经比较明确：

- 用 RealSense 获取彩色图像和深度图。
- 用 YOLOv8 检测目标。
- 提取目标框中心点。
- 结合对齐后的深度信息估计目标距离。
- 将目标位置转换为更适合控制或跟踪的空间坐标表示。

目前仓库里还没有形成正式的工程结构，更像是按功能逐步验证的实验记录。也正因为这样，README 更适合先承担“开发地图”的作用。

## 你之前已经做过什么

下面是按脚本整理出来的实验轨迹。

| 文件 | 作用 | 说明 |
| --- | --- | --- |
| `test/example_argparse.py` | 命令行参数练习 | 验证了 `argparse` 的基本用法，为后续做可配置脚本打基础。 |
| `test/test_pyrealsense.py` | RealSense 取流测试 | 跑通了彩色流和深度流的读取与显示。 |
| `test/test_depth.py` | 深度对齐与距离读取 | 完成了深度图和彩色图对齐，并尝试读取中心点及 ROI 平均深度。 |
| `test/test_YOLO.py` | YOLO 静态图测试 | 基于 `image.jpg` 和 `yolov8n.pt` 跑通了基础目标检测。 |
| `test/test_axis.py` | 检测框中心点提取 | 从 YOLO 输出中拿到了类别、置信度、边框和中心点。 |
| `test/test_polar.py` | 像素坐标转空间坐标 | 通过内参和深度值，将像素点转换为相机坐标和极坐标。 |
| `test/test_CapDet.py` | 摄像头实时检测 | 把 RealSense 彩色流和 YOLO 推理接起来，并输出 `person` 的中心点。 |
| `test/version_1.py` | 原型整合版本 | 将检测类别输入、目标中心点、距离估计和极坐标计算整合成单文件流程。 |

如果你下次继续开发，最值得先看的入口文件是 `test/version_1.py`，因为它最接近完整链路。

## 现有能力总结

按功能拆开看，你已经完成了这些关键验证：

- 相机输入：可以稳定读取 RealSense 彩色流和深度流。
- 检测能力：可以在静态图和实时图像上运行 YOLOv8。
- 几何信息：可以从检测框得到中心点。
- 深度能力：可以在目标点附近读取并平均深度值，降低单点噪声。
- 空间表达：可以把目标位置转换为 `r / azimuth / elevation`。
- 参数化入口：已经开始尝试让脚本支持命令行输入目标类别。

这说明你不是从零开始，而是已经完成了“关键技术链路验证”。

## 运行依赖

根据当前脚本内容推断，项目至少依赖以下环境：

- Python
- Intel RealSense SDK / 兼容驱动环境
- `pyrealsense2`
- `numpy`
- `opencv-python`
- `ultralytics`

示例安装命令：

```bash
pip install numpy opencv-python ultralytics pyrealsense2
```

说明：

- `argparse` 是 Python 标准库，自带即可使用。
- `test/yolov8n.pt` 已经在仓库中，当前脚本默认直接读取本地模型文件。
- 若后续换模型，建议把模型路径做成配置项，而不是继续写死在脚本里。

## 当前阶段的几个问题

从后续开发的角度看，现在最需要整理的不是算法，而是工程结构：

- 代码都放在 `test/` 目录里，实验脚本和后续正式代码边界不清晰。
- 目前没有统一入口文件，主要逻辑还分散在多个验证脚本中。
- 配置项大多写死，例如分辨率、模型路径、默认类别等。
- `version_1.py` 虽然最完整，但仍是原型风格，函数之间耦合偏高。
- 仓库里还没有依赖清单、模块分层和真正的自动化测试。

其中一个很值得后续顺手修的点是：`version_1.py` 中的 `person_distance()` 依赖外部 `depth_frame`，这会让函数复用和重构变得比较别扭。

## 建议的下一步

如果你准备继续往“可维护项目”推进，建议按这个顺序整理：

1. 先把 `version_1.py` 作为主参考，确认它就是你要继续迭代的基础版本。
2. 新建正式源码目录，例如 `src/`，把功能拆成相机、检测、测距、坐标转换几个模块。
3. 把现在的 `test/` 重命名为 `experiments/` 或 `sandbox/`，保留实验记录但避免和真正测试混淆。
4. 增加 `requirements.txt` 或 `pyproject.toml`，把依赖固定下来。
5. 最后再补一个主入口脚本，比如 `main.py`，统一调用各个模块。

## 一个更清晰的开发方向

如果后续按工程化方式整理，结构大致可以演进成这样：

```text
RIS/
├─ README.md
├─ requirements.txt
├─ src/
│  ├─ camera.py
│  ├─ detector.py
│  ├─ depth_utils.py
│  ├─ geometry.py
│  └─ main.py
└─ experiments/
   └─ ...现有验证脚本
```

这样做的好处是：

- 原型验证和正式开发分开。
- 每个能力模块都有明确职责。
- 后续更容易接控制逻辑、串口通信、机器人执行层或 UI。

## 一句话结论

这个仓库目前最有价值的成果，不是“已经做成了一个完整产品”，而是你已经把目标检测 + 深度测距 + 空间定位这条技术链路逐段验证过了。下一步最值得做的，就是把这些验证结果从脚本集合，整理成真正可维护的项目结构。
